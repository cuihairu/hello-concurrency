# 可靠性设计

高并发系统跑在会失败的部件上：机器会宕、网络会断、磁盘会坏、时钟会漂。可靠性设计的目标不是「不出错」，而是**出错之后还能正确地服务**。四件事撑起这一章——容错机制、一致性与分布式锁、持久化与恢复、分布式事务，对应 README 规划目录第 10 章。

## 故障模型：先分清错的是什么

| 故障类型 | 表现 | 对策 |
|----------|------|------|
| **崩溃失败** | 进程或机器彻底停摆 | 冗余副本、健康检查、自动重启 |
| **网络分区** | 节点间时通时不通 | 多数派决策，显式处理分区 |
| **慢节点/超时** | 请求迟迟不回，结果未知 | 超时 + 重试加抖动 + 熔断 |
| **部分失败** | 一次分布式调用只成功了一半 | 幂等键、对账、事务性发件箱 |
| **拜占庭** | 节点返回错误数据 | 校验与签名，本文不展开 |

两条容易被忽略的事实：**超时不等于失败**——调用超时后，对方可能已经执行成功，重试前必须先回答「重复执行有没有害」；**分区不是「对方挂了」**——网络不通与节点宕机在客户端看来无法区分，这正是后面脑裂问题的根源。

## 容错机制：冗余、检测与切换

高可用靠冗余，冗余的形态决定切换方式：

| 形态 | 结构 | 切换 | 一致性代价 |
|------|------|------|-----------|
| **主从热备** | 一个写主、若干只读从 | 探活后提升从节点 | 提升瞬间可能丢确认过的写 |
| **多主** | 多节点都能写 | 无切换，但要合并冲突 | 冲突解决（CRDT、业务规则） |
| **无主（仲裁）** | 每个节点可写，写入多数派 | 无单点，天然可切换 | 写延迟随副本数上升 |

**检测靠租约而不是心跳**：心跳只能说「一段时间没收到」，租约（lease）是「我保证这段时间内你是主」。两者都可能误判，所以写路径还要配 **fencing token**——租约发放时附带单调递增的令牌，存储端拒绝旧令牌的写入。持锁进程 GC 停顿几十秒后拿着过期租约回来写数据，就是没有 token 时的真实事故。Facebook 的 Memcache lease 机制处理缓存失效与重新填充的竞态，是同一思路在缓存层的应用（见[场景调研](../research/applications.md)）。

检测与切换之外还有**降级**：依赖故障时返回默认值、关掉非核心功能、舱壁隔离把故障域切小——手段清单在[知识点总纲的流量治理一节](../knowledge.md)。

## 一致性与分布式锁

一致性是谱系不是开关：

| 级别 | 保证 | 代价 | 典型场景 |
|------|------|------|----------|
| **线性一致** | 全局单一顺序，读到最新写 | 每次读写过多数派，延迟最高 | 锁、选主、库存扣减 |
| **因果一致** | 有因果关系的操作有序 | 需维护因果元数据 | 社交流、评论树 |
| **最终一致** | 停止写入后终将收敛 | 延迟最低 | 计数、日志、地域复制 |

**分布式锁的正确实现不是「SETNX 加过期时间」**。锁服务自身必须是多数派（单点 Redis 挂了锁就没了），锁要带 fencing token，客户端本地时钟不可信——过期时间只能由持锁方自己估算，这是 Kleppmann《How to do distributed locking》一文的核心批评（红锁方案的争议也源于此）。工程上的经验法则：

| 手段 | 保证 | 何时够用 |
|------|------|----------|
| 分布式锁 + fencing | 互斥 | 强一致写路径，代价最高 |
| 租约 | 限时独占 | 能容忍租约过期后的重复执行 |
| 幂等键 | 至少一次执行下结果正确 | 大多数业务场景的默认答案 |

**能用幂等解决的，不要上锁**：锁是协调，幂等是自治。协调要付可用性代价，自治不用。

## 持久化与恢复

崩溃恢复的地基是 **WAL（预写日志）**：先追加日志再改数据，恢复时按日志重放或回滚。checkpoint 的作用是缩短重放窗口——恢复时间与「上次检查点到崩溃点」的日志量成正比。

| 指标 | 含义 | 典型目标 |
|------|------|----------|
| **RPO** | 最多能丢多少数据 | 决定复制与备份频率 |
| **RTO** | 恢复要花多久 | 决定切换与重放策略 |

备份只有**验证过恢复**的才算备份：打不开的备份文件、缺了 WAL 段的归档，都是在故障当天才暴露的定时炸弹。恢复演练要按 RTO 实测，不能按推算。

## 分布式事务

| 模式 | 一致性 | 代价 | 适用 |
|------|--------|------|------|
| **两阶段提交（2PC）** | 强一致 | 协调者单点、参与者阻塞等待 | 短事务、同机房，XA 场景 |
| **Saga（补偿事务）** | 最终一致 | 每步要有逆操作，无隔离 | 长流程：下单、支付、履约 |
| **本地消息表** | 至少一次 | 消费端必须幂等 | 业务库与消息队列联动 |
| **TCC** | 最终一致 | 业务侵入，三段式实现 | 资金类需要冻结语义的场景 |

2PC 的阻塞在协调者崩溃时最致命：参与者持锁等待，整条链路停摆。所以跨机房、长流程的事务都在往 Saga 与本地消息表走——**用可补偿换掉阻塞，用幂等换掉隔离**。这套做法的理论前提是承认「网络不可靠时恰好一次不存在」，只能做到至少一次加幂等（Helland《Idempotence Is Not a Medical Condition》）。

## 陷阱

| 陷阱 | 后果 | 修正 |
|------|------|------|
| 重试治超时 | 超时的请求可能已执行，重复扣款、重复发消息 | 幂等键 + 重试加抖动，先回答「重复执行有没有害」 |
| 锁没有 fencing token | 租约过期后旧主回来继续写，双写 | token 单调递增，存储端校验拒绝旧令牌 |
| 把分区当宕机 | 少数派自选为主，脑裂双写 | 只有多数派能当选，分区恢复后服从多数派 |
| 2PC 协调者无高可用 | 协调者崩溃，参与者全部持锁阻塞 | 缩短事务，或换 Saga / 本地消息表 |
| 备份从未恢复验证 | 故障时才发现备份不可用 | 定期恢复演练，RPO/RTO 实测不推算 |
| 主从切换从不演练 | 真故障时切换脚本跑不通，RTO 变 RTO×N | 定期演练，切换纳入发布流程 |
| Saga 补偿失败无兜底 | 半完成状态永久悬挂 | 补偿重试 + 人工干预通道 + 对账 |

## 本章小结

可靠性设计的主线是三条：**失败是常态**，所以超时、重试、降级是常态代码而不是异常路径；**超时不等于失败**，所以幂等先于重试、fencing 先于信任租约；**强一致要用代价换**，所以一致性级别是业务决策而不是技术默认。单机的[锁与同步原语](../sync/locks.md)解决「多个线程怎么不打架」，本章解决「多台机器打起架来怎么不丢正确性」——前者是并发问题，后者是分布式问题，工程上后者总是叠加在前者之上。
