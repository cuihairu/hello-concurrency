# 数据并行

数据并行是《七周七并发模型》第 7 章的主题：**同一份程序，施加到数据的每个分片上**。任务是规则的，并行来自数据本身；与 Actor/CSP 这类「任务并行」——不同任务干不同的事——方向相反。

## 两种并行

| 维度 | 数据并行 | 任务并行 |
|------|---------|---------|
| 划分对象 | 数据分片 | 任务/功能 |
| 执行体行为 | 各分片跑同一段代码 | 各任务跑各自的逻辑 |
| 并行度上限 | 数据规模（容易上千路） | 任务拆分度（通常几十路） |
| 负载均衡 | 天然均匀（分片等大） | 需要调度器平衡异构任务 |
| 典型场景 | 图像处理、数值模拟、矩阵运算 | 微服务编排、流水线、事件处理 |

本仓其他并发模型页（[Actor](./actor.md)、[CSP](./csp.md)、[数据流](./dataflow.md)）都在任务并行一侧；数据并行是另一半地图。

## 硬件基础：从 SIMD 到 SIMT

- **SIMD**（单指令多数据）：CPU 的向量指令（x86 SSE/AVX、ARM NEON），一条指令同时算多个数据，宽 128/256/512 位
- **SIMT**（单指令多线程）：GPU 的执行模型，数千个轻量线程分批执行同一指令；NVIDIA 以 32 线程为一个 warp 调度

GPU 与 CPU 的设计取向相反：CPU 用大缓存与乱序执行压低单线程延迟，GPU 用海量线程隐藏访存延迟——某个线程等内存时调度器立刻切换到别的 warp。吞吐与延迟之争，决定了各自擅长的负载。

## OpenCL 编程模型

OpenCL 是 Khronos 维护的开放标准，一套 API 面向 CPU/GPU/FPGA 多种设备；书第 7 章用它做 GPGPU 教学载体。

```
Host（CPU）                          Device（GPU）
──────────                          ──────────────
1. 选平台与设备
2. 创建 Context + 命令队列
3. 分配 Buffer，拷入数据  ─────────→  Global Memory
4. 提交 kernel                       NDRange 划分：
                                     ┌─────────────┐
                                     │ WG  WG  WG  │  ← work-group
                                     │ WI WI WI WI │ ← work-item
                                     └─────────────┘
5. 拷回结果               ←─────────
```

| 概念 | 含义 | CUDA 对应 |
|------|------|-----------|
| work-item | 最小执行单元，处理一个（或一片）数据 | thread |
| work-group | work-item 分组，组内可同步、共享本地内存 | block |
| NDRange | 全局索引空间（1/2/3 维） | grid |
| local memory | work-group 内共享的高速片上内存 | shared memory |

kernel 是跑在设备上的函数，每个 work-item 用自己的全局 id 算出负责哪个数据分片——「同一段代码 × 不同数据」正是数据并行的直接翻译。

## 经典模式：归约

求和、求最值这类「多输入折叠成单输出」操作，朴素写法是串行累加（O(n) 步）；并行写法是**树形归约**（O(log n) 步）：

```
串行:  1 → +2 → +3 → +4 → ...        n 步
树形:  (1+2)(3+4)(5+6)(7+8)          log n 步
        ↓      ↓
        (a+b) (c+d)
            ↓
           sum
```

树形归约的关键约束：合并操作必须满足**结合律**。浮点加法不满足严格结合律，并行归约与串行累加的结果可能有舍入差——数值敏感场景要预留容差，这不是 bug。归约是 [MapReduce 与 Lambda 架构](./lambda-architecture.md)里 reduce 语义的单机原型。

## 性能特征

| 因素 | 影响 |
|------|------|
| 数据传输 | host↔device 走 PCIe，带宽远低于显存内部，小数据或多次往返会把计算收益吃光 |
| 分支发散 | 同一 warp 内 if/else 两路都执行再各自掩掉，分支越多有效吞吐越低 |
| 访存模式 | 相邻 work-item 访问相邻地址才能合并传输（coalescing），跨步访问带宽骤降 |
| 占用率 | 寄存器与共享内存用量决定驻留 warp 数，驻留不足则延迟隐藏失效 |

## 适用性判断

| 适合 | 不适合 |
|------|--------|
| 计算密集：图像、物理模拟、矩阵运算 | 分支密集的逻辑代码 |
| 规则数据结构：稠密数组、规则网格 | 指针追逐：链表、树遍历 |
| 数据量大，传输开销占比低 | 小数据（启动 kernel 的开销都不值） |
| 操作彼此独立，或归约/扫描这类已知模式 | 步骤间强串行依赖 |

## 陷阱

| 陷阱 | 后果 | 修正 |
|------|------|------|
| 忽视传输成本 | GPU 算得快，传得慢，总时长反超 CPU | 数据驻留设备端，批量传输，用 pinned memory |
| kernel 里写复杂分支 | 发散拖垮整个 warp | 逻辑分支留在 host，或按分支重组数据 |
| 忽略结合律 | 浮点归约结果与串行版不一致被当 bug | 认它是并行归约的固有属性，按容差验收 |
| work-group 内无同步就用共享内存 | 数据竞争，结果不确定 | 组内屏障（barrier）后再读 |
| 用 CPU 思维写 kernel | 每线程做复杂控制流，寄存器爆、占用率掉 | 每线程做简单均匀的工作，控制流上移 |

## 与本仓其他页的关系

- [函数式并发](./functional.md)的 fold/pmap 是多核上的数据并行，本章延伸到异构加速器
- [数据流模型](./dataflow.md)是编排抽象（DAG 调度），与本章正交：数据流引擎的每个节点内部常用数据并行执行
- [Amdahl 定律](../basics/concepts.md)：串行部分决定加速上限，GPU 救不了串行代码

## 本章小结

数据并行把并行的来源从「任务拆分」换成「数据分片」，代价是算法必须迁就硬件的执行与访存模型。工程判断三步走：计算是否密集、数据是否规则、分支是否稀少——三者皆备才考虑 GPU；否则多核数据并行（[函数式并发](./functional.md)的 fold）通常是更便宜的答案。
