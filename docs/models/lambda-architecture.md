# Lambda 架构

Lambda 架构是《七周七并发模型》第 8 章的主题，Nathan Marz 在 BackType/Twitter 处理全量数据时提出。它回答的问题是：**数据太大、查询太多，实时算不完怎么办**——答案是批处理层慢算全量、速度层快算增量，两层结果在查询时合并。

## 核心结构

```
            ┌─────────────── 批处理层 ───────────────┐
  新数据 →  │ 主数据集（不可变、只追加）              │
            │   ↓ MapReduce 批任务，周期重算          │
            │ 批视图                                  │
            └──────────────┬─────────────────────────┘
                           ↓ 合并
  查询 ──────────────→ 服务层 ──→ 结果
                           ↑ 合并
            ┌──────────────┴─────────────────────────┐
            │ 速度层：处理批处理窗口之外的增量          │
            │ （Storm/流计算，实时视图）               │
            └─────────────────────────────────────────┘
```

三层职责：

| 层 | 职责 | 时延 | 技术 |
|----|------|------|------|
| **批处理层** | 存全量主数据集，周期性重算批视图 | 小时级 | Hadoop/MapReduce、Spark |
| **速度层** | 补上批处理窗口内的增量，算实时视图 | 秒级 | Storm、Flink、Spark Streaming |
| **服务层** | 合并批视图与实时视图，供查询 | — | 专用数据库（ElephantDB 等） |

## 关键设计决定

### 不可变主数据集

一切数据只追加、不修改，任何时刻可从主数据集重算任何视图。这带来三个性质：

- **容错简单**：机器坏了重算那一批，不需要复杂的分布式恢复协议
- **人算容错**：代码写错了，改掉重算，错误数据被完全覆盖——Marz 称之为 human-fault tolerance
- **演进自由**：视图算法升级了，全量重算一遍即可，旧数据从不变质

这正是[函数式并发](./functional.md)的不可变思想搬到分布式数据系统：数据不改，并发（以及故障恢复）就从「控制」变成「重算」。

### 批视图 = 预计算

查询不碰原始数据，只查预计算好的视图（索引、聚合表）。视图函数必须是**任意重算幂等**的：同一份主数据集输入，输出视图永远相同。

### 两层的合并点在查询时

批视图旧而准，实时视图新而糙，服务层把两者拼起来回答查询。批处理追上之后，速度层对应增量作废。

## 代价与批评

| 代价 | 说明 |
|------|------|
| **同一逻辑写两遍** | 批处理与速度层用不同框架，同一聚合逻辑要双实现、双维护，改口径要改两处 |
| 两套系统运维 | Hadoop + 流计算 + 服务层，组件多 |
| 重算成本 | 全量重算耗资源，批处理窗口是延迟与成本折中 |

对「两遍逻辑」的标准回应是 **Kappa 架构**（Jay Kreps，2014）：去掉批处理层，只留流计算，需要重算时用新消费组从头重放日志（Kafka 保留全量）。Kappa 换来单一代码路径，代价是把重算压力压给流系统。两者是同一问题的不同取舍，不是替代关系：批处理窗口可控、重算成本可预算时 Lambda 更稳；逻辑变更频繁、运维力量薄时 Kappa 更省。

## 与并发模型的关系

Lambda 架构不引入新的同步原语，它的并发性来自三层结构：

- 批任务之间、流分片之间天然并行——[数据并行](./data-parallel.md)（分片跑同一段聚合逻辑）与 MapReduce 的 reduce 语义（结合律归约）同源
- 不可变主数据集让读写无竞争，是[函数式并发](./functional.md)的不可变性在大数据规模上的应用
- 批与流两条路径是[数据流模型](./dataflow.md)的 DAG 在系统级的表现

## 适用性判断

| 适合 | 不适合 |
|------|--------|
| 海量历史数据 + 实时性要求并存的查询 | 纯实时小数据（一套流计算就够） |
| 视图可全量重算，聚合逻辑稳定 | 强事务更新（不可变主数据集帮不上） |
| 容错要求高，错误必须可完全追溯 | 团队维护不动两套系统 |

## 本章小结

Lambda 架构把「算不完」拆成「慢而全」与「快而增量」两条路径，靠不可变主数据集保证两者最终一致、错误可重算。它的高层抽象——批流分离、视图预计算、追加式存储——是理解现代数据系统（流批一体、物化视图、日志即数据库）的共同源头；Kappa 是它在流计算成熟后的简化方向。
