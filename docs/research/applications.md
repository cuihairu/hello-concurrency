# 应用场景调研：高并发服务与游戏服务器

README 里承诺讲应用场景，`chapter_1.md` 的 1.2 只给了一张六行的表。这一页把两类最常见的场景拆开：互联网高并发服务、游戏服务器，各自的并发形态、流量手段与坑，最后给出场景到本仓章节的映射。

## 场景一：高并发服务

指 Web 服务、微服务、网关、消息系统这类「大量短请求同时到达」的系统。它的并发形态是线程池加异步 IO：连接数远大于工作线程数，请求进来排队，处理完立刻还回去。腾讯云开发者社区那篇流量治理文章给的例子很直白：Tomcat 默认 200 个工作线程，请求多于线程时新请求只能在浏览器里转圈，连 Hello world 都拿不到响应。这其实就是最朴素的限流，只不过它限的是容器而不是业务。

### 流量治理的五个手段

| 手段 | 做什么 | 关键点 |
|------|--------|--------|
| 限流 | 给资源设数量上限，超出的缓冲或直接拒绝 | 常见算法：计数器、漏桶、令牌桶；计数器不平滑，工程里漏桶与令牌桶用得多。限流由服务提供方提供，保护的是底层资源 |
| 熔断 | 下游故障时切断调用，返回默认结果 | 由调用端提供，用在旁路请求上，防止 A→B→C 链路上一个 C 挂掉拖垮整条线程池 |
| 降级 | 从入口大范围关掉非核心流量 | 适合放在 Nginx、DNS 这种入口层；电商大促时先关评论、推荐 |
| 预热 | 新节点慢慢加量 | 刚启动的 JVM 没 JIT 编译、刚重启的 DB 缓存是冷的，直接接 1/N 流量就可能打挂 |
| 背压 | 被调用方持续反馈处理能力，调用方据此调速 | 比固定限流多一层反馈，TCP 滑动窗口是原型；Reactive Streams 把它做成了规范 |

这五件事在本仓的落点分别是：[线程池设计](/practice/thread-pool)（容量与拒绝策略）、[生产者-消费者](/practice/producer-consumer)（队列长度与背压策略）、[性能调优](/advanced/performance)（Little's Law 容量公式）。

### 分布式缓存这一侧

单机并发做完之后，高并发服务的第二层是把热点读移出数据库。Facebook 的 Memcache 集群（NSDI '13）是这条路线的标准答案：跨机房放热点对象缓存，用 lease 机制处理缓存失效与重新填充的竞态，避免同一个 key 被并发回源。本仓的 [并发数据结构](/advanced/data-structures) 讲到本地缓存的原子化更新，跨机房那一层不在范围内，但两者的竞态来源是同一种：读-改-写不原子。

### 这个场景考验什么

1. 队列深度和背压：队列无限增长等于把故障推迟到 OOM。
2. 临界区长度：锁里做网络调用，吞吐会断崖式下跌。
3. 伪共享与缓存行：计数器放一起更新，多核反而变慢，[性能调优](/advanced/performance) 一章有排查方法。
4. 优雅停机与滚动发布：连接没排空就下线，表现就是重启瞬间的报错尖峰。

## 场景二：游戏服务器

游戏服务器的并发形态和 Web 很不一样：单个玩家的操作是顺序的，跨玩家的交互才需要并发，而且状态高度共享（同一张地图上的坐标、血量、背包）。主流解法是把共享状态收进 actor，每个 actor 单线程处理消息，靠消息传递代替加锁。

### skynet 这条路线

[skynet 的 README](https://github.com/cloudwu/skynet) 自述是「a multi-user Lua framework supporting the actor model, often used in games」，并且「heavily used in the Chinese game industry」。C 写框架、Lua 写业务，每个 actor 是一个独立的 Lua 虚拟机加一个消息队列，调度器按公平轮转派发消息。腾讯云那篇设计文章把它拆成三块讲：Actor 模型、消息队列、actor 公平调度，另有热更新与网络层，适合构建大型多人在线游戏与实时应用。

对本仓的意义：[Actor 模型](/models/actor) 的「消息投递语义」「监管策略」「反模式与陷阱」三节可以直接用这类框架对照着读；actor 单线程内无共享可变状态这一点，和 [CSP](/models/csp) 的「通信不共享」是同一原则的两种写法。

### 游戏服务器特有的问题

| 问题 | 形态 | 常见处理 |
|------|------|----------|
| 逻辑帧与定时器 | 每帧推进世界，定时任务按帧号触发 | 单线程主循环加时间轮，避免在帧内做阻塞 IO |
| 状态同步 | 服务器向几十上百个客户端广播位置 | 快照插值、兴趣管理（只同步同屏对象）、按帧批量发送 |
| 广播风暴 | 一个事件触发 N 个客户端各发一次 | 合并写、分帧发送、带宽预算 |
| 断线重连 | 玩家掉线后状态还在 | 会话超时与状态快照回放 |
| 热更新 | 不停服改逻辑 | Lua/脚本层热替换，C 层不动 |
| 背压 | 慢客户端拖垮网络线程 | 写队列上限，超限踢人而不是阻塞 |

热点循环里要小心的是：帧循环对延迟抖动极敏感，GC 停顿与锁争用都会直接变成掉帧，这是[性能调优](/advanced/performance) 里「延迟分解」那套分析在游戏场景的具体形态。
