# 并发与安全

并发问题不只丢数据，还能丢权限、丢钱、丢机密。竞态（race）是安全漏洞的一大来源：**检查与使用之间的那段时间差**，就是攻击者的操作窗口。安全界的经典案例几乎全是并发问题——symlink 攻击、内核 double-fetch、缓存侧信道，本质都是「两步之间状态被改了」。本页对应 README 规划目录第 11 章。

## 竞态如何变成漏洞

| 漏洞形态 | 竞态在哪 | 后果 |
|----------|----------|------|
| **TOCTOU**（time-of-check to time-of-use） | 权限检查与实际操作之间，文件被换成 symlink | 越权读写，提权 |
| **double-fetch** | 用户态与内核态各读一次缓冲区，两次之间长度被改 | 内核堆越界，提权 |
| **未同步的共享状态** | 校验用的配置与执行用的配置不是同一份 | 绕过校验 |
| **初始化竞态** | 对象在初始化完成前被其他线程观察到 | 读到脏数据、绕过不变式 |
| **随机数/密钥竞争** | 多线程共享同一个伪随机状态 | 密钥可预测，加密形同虚设 |

共同结构是**两步操作不是原子的**：单机并发页讲的临界区问题，在安全语境下多了一层含义——攻击者是**主动制造交错**的那一方，而不是随机的调度抖动。所以「竞态概率很低」不是安全论证。

**修法只有一条：把检查和使用放进同一个原子操作里。**

```
# 错：检查与使用分离，窗口任人穿越
if (os.access(path, W_OK)):
    write(path, data)     # 此刻 path 可以指向任何地方

# 对：一次系统调用完成检查+使用，或用 O_NOFOLLOW / openat 消掉窗口
fd = os.open(path, O_WRONLY | O_NOFOLLOW)   # 打开即校验，fd 不再跟随改名
write(fd, data)
```

内核 double-fetch 的对策同理：缓冲区**只拷贝一次**（copy_from_user 一次到位），此后一律用内核侧副本。

## 死锁与资源耗尽也是安全问题

并发的可用性面同样是攻击面：

| 攻击 | 机制 | 对策 |
|------|------|------|
| **锁耗尽** | 恶意请求触发大量等待锁的慢路径 | 锁等待超时、有界等待队列 |
| **Slowloris** | 慢速占住连接，每连接一线程的模型被打满 | 连接数上限、读超时、事件驱动 |
| **无界队列打爆内存** | 请求速率超过处理速率，队列无限涨 | 有界队列 + 拒绝策略，见[线程池设计](../practice/thread-pool.md) |
| **死锁触发** | 攻击者构造特定交错，让服务自锁 | 锁序、超时获取（`tryLock` 带超时） |
| **协程/连接泄漏** | 每次请求留一个不回收的任务 | 资源上限 + 泄漏检测，见[可靠性设计](../practice/reliability.md) |

这类漏洞的共同修法是**给每个共享资源设上限**：线程数、队列长度、锁等待时间、连接数都要有显式上限。无界就是可被耗尽——这与[生产者-消费者](../practice/producer-consumer.md)的「有界是铁律」是同一条约束，只是安全场景里越界者是攻击者。

## 侧信道：竞争之外的「同时」

即使没有共享可变状态，「同时执行」本身也会泄漏信息：

| 侧信道 | 原理 | 对策 |
|--------|------|------|
| **缓存侧信道**（Flush+Reload、Spectre） | 竞争同一缓存行，测访问时间反推密钥 | 常量时间比较、清缓存（`clflush`）、隔离（core scheduling） |
| **时序攻击** | `str` 比较提前返回，逐字节猜出密钥 | 用固定时间比较（`MessageDigest.isEqual`、`CRYPTO_memcmp`） |
| **资源竞争探测** | 观察共享锁/队列的占用时间，推断他人负载 | 抖动、隔离资源池 |

并发页这里只强调一条工程纪律：**安全相关的比较必须常量时间**。字符串相等比较在多数语言里是提前返回的，这不是实现瑕疵而是优化本性——放到密钥比较上就是漏洞。常量时间比较不是本仓主题，落点在各语言的标准库函数，见[编程语言与并发支持](../advanced/languages.md)。

## 安全编程实践

按 Saltzer & Schroeder 的保护机制原则，落到并发上：

| 原则 | 并发语境的形态 |
|------|----------------|
| **经济性** | 共享可变状态最小化——能不可变就不可变，见[函数式并发](../models/functional.md) |
| **完全中介** | 每次访问都重新检查，缓存的授权结论要绑定上下文与过期 |
| **失败安全** | 默认拒绝：锁超时、队列满、token 过期时，一律拒绝而不是放行 |
| **心理可接受** | 正确性靠类型系统与封装兜底，不靠「调用方记得加锁」 |
| **特权分离** | 校验线程与执行线程不同权限，攻击者要跨两步 |

三条落地清单：

1. **共享状态必须有归属**：要么封装在单个 actor/线程内（见[Actor 模型](../models/actor.md)），要么有明确的锁保护（见[锁](../sync/locks.md)），没有第三种。
2. **检查与使用同原子**：所有权限、限流、余额的检查，紧邻的使用必须在同一临界区或同一原子操作内。
3. **每个资源有上限**：线程、队列、连接、锁等待，全部显式有界，超限拒绝。

## 检测工具

| 工具 | 检什么 | 用在哪 |
|------|--------|--------|
| **ThreadSanitizer（TSan）** | 数据竞争、锁序错误 | C/C++/Go/Rust（`-fsanitize=thread`、`-race`） |
| **Helgrind / DRD** | 数据竞争与死锁 | Valgrind 套件，C/C++ |
| **jcstress** | 并发代码的真实交错结果 | JVM，OpenJDK 官方工具 |
| **rr / 时间旅行调试** | 复现偶发竞态 | Linux x86 |
| **lockdep** | 锁序违反（运行时告警） | Linux 内核，可移植到部分用户态 |

共同局限：**检测器只覆盖跑过的交错**。竞态类漏洞的根治靠结构（封装、原子性、不可变），检测是补充不是替代——这与[无锁编程](../advanced/lockfree.md)页「正确性靠模型不靠运气」是同一句话。

## 陷阱

| 陷阱 | 后果 | 修正 |
|------|------|------|
| 「竞态概率低所以安全」 | 攻击者能主动制造交错，不是等随机抖动 | 假设交错可达，按原子性论证 |
| 权限检查后重新打开文件 | TOCTOU，路径被换 | 一次 open 拿 fd，之后只用 fd |
| 缓冲区读两次 | 内核 double-fetch 越界 | 只拷贝一次，用内核侧副本 |
| 用 `str` 比较比较密钥 | 时序攻击逐字节猜出密钥 | 固定时间比较函数 |
| 共享 `Random`/密钥生成器 | 多线程共享状态，密钥可预测 | 每线程独立实例或用 CSPRNG |
| 无界队列扛流量 | 攻击者把内存打满 | 有界 + 拒绝，见[线程池设计](../practice/thread-pool.md) |
| 只靠 TSan 绿灯 | 检测器只覆盖跑过的交错 | 结构性保证为主，检测为辅 |

## 本章小结

并发安全的一句话总结：**攻击者会主动制造交错，所以「偶发」不成立**。三类漏洞各有修法——TOCTOU 与 double-fetch 用「检查与使用同原子」根治，资源耗尽用「每个共享资源显式有界」根治，时序与缓存侧信道用「常量时间 + 隔离」压制。这些约束不是新增的纪律，而是[临界区](../basics/critical-section.md)、[有界缓冲](../practice/producer-consumer.md)与[可靠性设计](../practice/reliability.md)已有原则在攻击者面前的重申：能被并发改变的状态，就能被并发攻击。
